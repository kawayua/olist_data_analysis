# 电商增长、留存与复购分析平台设计文档

## 1. 项目定位

项目名称为 **E-Commerce Growth, Retention & Repurchase Analytics Platform**。项目面向数据分析岗位，以业务分析为主体，以 Python 工程、机器学习和可审计分析 Agent 作为差异化能力。

工作量按以下比例控制：

- 70%：数据建模、指标体系、探索分析、统计验证和交互式 Dashboard。
- 20%：首购客户 90 天复购倾向预测与营销策略模拟。
- 10%：自然语言问数、自动图表和业务解释 Agent。

项目需要回答的核心业务问题是：

> Olist 的收入增长来自哪里，客户为什么很少复购，哪些客户最值得优先运营，以及提升复购可能带来多少增量收入？

## 2. 目标与非目标

### 2.1 项目目标

1. 从多张真实业务表建立可追溯、可复用的分析数据模型。
2. 用一致的指标口径分析收入增长、客户结构、留存复购、商品表现和履约体验。
3. 使用统计方法区分描述性现象、相关性证据和因果结论。
4. 构建无时间泄漏的复购预测模型，并将模型输出转换成营销资源分配建议。
5. 构建受控、可审计的自然语言分析 Agent，而不是只包装一个聊天接口。
6. 形成可运行、可测试、可部署，并可在面试中完整讲解的作品集项目。

### 2.2 非目标

- 不开发完整电商交易网站。
- 不把一次购买直接定义成传统合同型“流失”。
- 不声称观察性数据证明了因果关系。
- 不为了模型分数使用会破坏时间结构或业务真实性的数据处理方式。
- 不构建复杂多 Agent 系统。
- 不同时维护 Streamlit 和 Power BI 两套完整前端。

## 3. 数据来源与限制

主数据使用 Olist Brazilian E-Commerce Public Dataset，包含约 10 万笔 2016 至 2018 年的匿名订单，以及客户、订单、订单商品、支付、评价、商品、卖家、地理位置和品类翻译等关联表。

- GitHub 数据说明镜像：<https://github.com/spdrio/Brazilian-E-Commerce-Public-Dataset-by-Olist>
- 原始数据来源：<https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce>
- 可选卖家营销漏斗：<https://www.kaggle.com/datasets/olistbr/marketing-funnel-olist>

项目将提供可重复的数据下载或放置说明、文件清单和校验逻辑。原始大文件默认不提交到 Git 仓库；发布时保留来源和许可说明，并在重新分发数据前核对原始数据页的许可条件。

已知限制如下：

- 数据只覆盖有限历史区间，不能代表当前 Olist 经营状况。
- 绝大多数客户只出现一次，传统 RFM 的 Frequency 区分能力有限，类别也高度不平衡。
- 数据没有完整的网站访问、广告曝光、消费者注册和营销触达记录，不能计算消费者侧完整获客漏斗。
- Marketing Funnel 数据描述卖家线索，不应与消费者转化率混为一谈。
- 数据集起止边界可能是不完整月份，趋势分析默认排除不完整边界月份或显式标注。

## 4. 技术架构

```text
Olist CSV
   |
   v
Python ingestion + validation
   |
   v
PostgreSQL
   |-- raw        原始数据与导入元数据
   |-- staging    类型转换、去重和异常标记
   |-- warehouse  事实表与维度表
   `-- marts      指标、分析和机器学习数据集
   |
   +--> Python analytics / statistical tests
   +--> ML training and batch scoring
   `--> Streamlit + Plotly
             |
             `--> Analysis Agent tools
```

主要技术选型：

- Python：数据导入、验证、分析服务、机器学习、Agent 和应用编排。
- Pandas：中等规模数据处理与探索分析。
- SQLAlchemy 与 PostgreSQL 驱动：连接管理、参数化查询和事务控制。
- PostgreSQL：分层数据模型、分析 SQL 和只读 Agent 查询。
- Streamlit 与 Plotly：交互式分析应用和图表。
- scikit-learn：预处理 Pipeline、基线模型、评估和概率校准。
- LightGBM 或 XGBoost：候选提升模型，最终根据环境和验证结果选择。
- Pydantic：配置、工具参数与 Agent 结构化输出校验。
- pytest：单元测试、集成测试和指标回归测试。
- Docker Compose：统一 PostgreSQL 与应用运行环境。

模型访问通过兼容 OpenAI API 的独立适配器实现，使用 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 和 `LLM_API_STYLE` 配置，业务模块不绑定具体供应商或模型。

## 6. 数据模型与粒度

### 6.1 原始层和暂存层

`raw` 层按源文件一对一保存数据，并记录文件名、导入批次和导入时间。`staging` 层负责字段类型、时间格式、缺失值、重复记录和业务异常标记，不静默删除无法解释的数据。

### 6.2 仓库层

核心实体包括：

- `dim_customer`：以 `customer_unique_id` 表示可跨订单识别的客户。
- `dim_product`：商品属性和英文品类。
- `dim_seller`：卖家及所在地。
- `dim_date`：日期、月份、季度、星期等时间属性。
- `fact_orders`：一行一笔订单，保存状态和关键时间戳。
- `fact_order_items`：一行一个订单商品，保存商品金额、运费和卖家。
- `fact_payments`：保留支付序号粒度，并另建订单支付汇总。
- `fact_reviews`：保留评价粒度和评价产生时间。

订单、订单商品、支付和评价的粒度不同。任何跨粒度计算必须先在各自粒度聚合，再按订单连接，防止金额被重复计算。

### 6.3 分析集市

- `mart_monthly_growth`：月度收入、订单、客户、客单价和新老客户贡献。
- `mart_customer_360`：客户首购、最近购买、订单、金额、品类和体验特征。
- `mart_cohort_retention`：首购 Cohort 和 30/60/90 天复购指标。
- `mart_product_performance`：品类和商品的销售、评价、运费与履约表现。
- `mart_delivery_experience`：配送时长、延迟、评价和复购关联数据。
- `mart_ml_customer_features`：按预测时点生成的无泄漏特征与标签。

## 7. 指标口径

- 商品销售额：已交付订单商品的 `SUM(price)`。
- 运费：已交付订单商品的 `SUM(freight_value)`。
- 实付金额：先在支付粒度按订单汇总 `SUM(payment_value)`，再汇总到分析维度。
- 有效订单：默认状态为 `delivered` 的不同 `order_id`；其他状态单独分析。
- 客户数：不同 `customer_unique_id` 数量。
- 新客户：首次有效购买发生在当前分析周期的客户。
- 老客户：首次有效购买早于当前周期且当前周期再次购买的客户。
- 客单价：有效订单实付金额除以有效订单数。
- 90 天复购率：拥有完整 90 天观察期的首购客户中，在首购后 90 天内再次有效购买的比例。
- 延迟天数：实际送达时间减预计送达时间，正值表示延迟。
- RFM：以统一分析截止日计算 Recency、Frequency 和 Monetary；报告中说明 Frequency 区分能力受低复购率限制。

所有指标定义集中维护，并由 SQL 测试和少量人工核算样例验证。Dashboard 和 Agent 必须复用同一指标来源。

## 8. 数据分析与 Dashboard

Streamlit 第一阶段包含五个页面：

1. **经营总览**：GMV、商品销售额、订单、客户、客单价、环比与数据完整性提示。
2. **增长诊断**：新老客户收入、地区与品类贡献、增长贡献拆解。
3. **留存复购**：Cohort 热力图、30/60/90 天复购率、复购间隔和边界样本说明。
4. **客户价值**：RFM 分层、客户生命周期、收入集中度和分层运营建议。
5. **商品与履约**：品类表现、运费比例、配送延迟、评价与复购的关联分析。

每个页面遵循相同的分析表达顺序：指标现状、趋势或分群、异常定位、可能原因、证据限制和行动建议。所有页面提供指标解释、时间范围、筛选条件和数据更新时间。

策略模拟器允许用户设置可触达客户数、触达成本、毛利率和预期复购提升，输出预期增量订单、增量收入、成本、利润和 ROI。模拟结果明确标注为情景假设，不作为因果预测。

## 9. 机器学习设计

任务定义为：以客户首笔订单的实际送达时间作为预测时点，预测其是否会在此后的 90 天内再次购买。没有实际送达时间的订单不进入这一监督学习任务，而在履约分析中单独处理。

### 9.1 样本与时间

- 特征只使用首笔订单实际送达时已经产生的信息。
- 标签观察预测时点后的未来 90 天是否出现第二笔有效订单。
- 数据集末尾没有完整 90 天观察期的客户不进入监督训练。
- 训练、验证和测试按首购时间顺序切分，不随机打散。
- 评价只有在时间戳不晚于预测时点时才能作为该样本特征；否则排除。

### 9.2 特征

特征覆盖首单消费、运费、支付方式、分期、商品与品类、配送体验、客户位置、卖家距离和时间属性。所有特征提供定义、来源字段、可用时点和缺失处理说明。

### 9.3 模型与评估

依次比较业务规则、Logistic Regression、Random Forest 和梯度提升模型。主要指标为 PR-AUC、Precision@Top-K、Recall@Top-K、Lift@10% 和概率校准；ROC-AUC 仅作为补充，不使用 Accuracy 作为主要结论。

默认先使用类别权重、阈值选择和概率校准，不把 SMOTE 作为默认方案。模型解释使用 Logistic Regression 系数、SHAP 和分群统计，并明确解释预测关联而非因果效应。

### 9.4 产品化输出

训练产物保存为包含预处理和分类器的完整 Pipeline。Streamlit 预测页面展示客户复购概率、风险等级、主要影响因素、Top-K 目标名单和营销 ROI 情景，并允许下载筛选结果。

## 10. 分析 Agent 设计

Agent 负责理解问题、选择指标、调用工具、验证结果、选择图表和解释业务含义。它不能脱离查询结果回答数据问题。

首期工具包括：

- `get_metric_definition`
- `run_safe_sql`
- `create_chart`
- `predict_repurchase`
- `simulate_campaign`

SQL 安全策略包括：仅允许单条 `SELECT`；仅允许白名单 `marts` 视图；禁止系统表、数据定义与数据修改语句；设置查询超时与行数上限；使用独立只读数据库账号。图表工具只接受预定义类型和结构化参数，不执行模型生成的 Python 代码。

每次回答显示指标口径、时间范围、SQL、结果表、图表和工具调用摘要。系统准备约 30 个固定问题，评估指标选择正确率、SQL 执行成功率、数值准确率、不可回答识别率、响应时间和调用成本。

Agent 优先使用兼容 API 的 function calling；若供应商不支持，则通过严格 JSON Schema 输出适配。相关设计参考：<https://developers.openai.com/api/docs/guides/function-calling>。

## 11. 数据质量、错误处理与可观测性

每次导入至少检查：文件存在性、列结构、主键重复、外键孤儿、时间顺序、金额范围、状态枚举和关键字段缺失。检查结果写入质量日志，并在 Streamlit 数据质量区域展示。

导入使用批次标识和数据库事务。严重结构错误终止该批次并保留错误报告；可解释的业务异常保留原记录并增加标志字段。应用向用户显示可操作的错误信息，详细堆栈只写入开发日志，密钥不得进入日志或 Git。

模型训练记录数据时间范围、特征版本、参数、指标和产物路径。Agent 记录脱敏后的问题、工具名称、查询耗时、返回行数和错误类型，以支持评测和调试。

## 12. 测试与验收

测试分为：

- 单元测试：指标函数、时间窗口、特征构造、SQL 安全规则和 ROI 公式。
- 数据测试：唯一性、非空、引用完整性、金额守恒和关键指标合理范围。
- 集成测试：CSV 到 PostgreSQL、集市到 Dashboard、模型加载与评分、Agent 工具调用。
- 指标回归测试：对固定样本验证 SQL 与 Python 得出相同结果。
- Agent 评测：固定问题的数值、指标、SQL、安全拒绝和不可回答表现。
- 手工验收：页面筛选一致性、空结果、边界月份、移动窗口和下载功能。

项目完成的最低标准为：全新环境可以依据 README 启动；数据流水线可重复运行；核心指标口径有测试；Dashboard 能讲清至少三个有证据的业务发现；模型严格按时间评估并优于业务基线；Agent 不执行写操作且通过固定问数集的主要用例。

## 13. 四周里程碑

- 第 1 周：环境、数据审计、PostgreSQL 分层建模和质量检查。
- 第 2 周：指标集市、SQL 分析、统计验证和 Dashboard 主页面。
- 第 3 周：机器学习样本、基线、候选模型、解释与策略模拟。
- 第 4 周：Agent、安全与评测、应用整合、测试、文档、部署和面试材料。

## 14. 教学与协作方式

每个实现步骤遵循以下循环：

1. 先解释该步骤解决的业务或工程问题。
2. 给出本次要掌握的概念和小任务。
3. 用户尝试后共同检查，或在用户授权时由 Codex 实现并逐段讲解。
4. 运行测试或查询，用可重复证据验收。
5. 记录踩坑、设计取舍和可用于面试的表达。

每周结束产出一次复盘，包括完成内容、核心发现、技术难点、下周风险和一段简历素材。项目最终产出 README、架构图、数据字典、指标字典、分析报告、模型卡、Agent 评测报告、部署说明和面试讲解提纲。

## 15. 主要风险与控制

- **低复购与类别不平衡**：调整为复购倾向任务，使用适当评估指标，并如实报告模型上限。
- **时间泄漏**：为每个特征记录可用时点，使用时间切分和标签观察期。
- **跨表重复聚合**：明确每张表粒度，连接前先聚合，并设置金额守恒测试。
- **一个月范围过大**：70/20/10 分阶段交付，任何阶段都保持可演示；Agent 只做一个受控工作流。
- **兼容 API 差异**：模型适配层隔离 API 风格，并提供无密钥的固定示例演示模式。
- **分析结论夸大**：区分事实、相关性、假设和因果结论，显示数据范围与限制。
